# AGENTS.md

Файл для ИИ-агентов, работающих с этим репозиторием. Основной язык проекта (код, комментарии, документация) — русский.

## Обзор проекта

**Mesh-доставка с хранением в ПВЗ** — проект для хакатона RWB (25–26 ноября 2026). Идея: ходовой товар хранится прямо в пунктах выдачи заказов (ПВЗ) и перемещается между ними попутно — теми же газелями, что развозят заказы из хаба. Остановка добавляется в маршрут, только когда это дешевле базовой схемы через хаб.

Репозиторий — монолит из трёх сервисов в Docker Compose: PostgreSQL, backend (FastAPI), frontend (React). Это каркас окружения, подготовленный до хакатона; большая часть предметной логики (остатки, заказы, проводки, сценарии) пишется командой на хакатоне.

Важные документы:

- `docs/01-task-and-rules.md` — задание и правила хакатона;
- `docs/02-business-model.md` — экономическая модель v2;
- `docs/03-architecture.md` — модули, модель данных (~19 таблиц), инварианты, двойная запись, ночной план газелей;
- `docs/04-scenarios.md` — пять сценариев и числа, которые должны сойтись;
- `CLAUDE.md` — краткие правила для ИИ-агентов (инварианты, команды);
- `DISCLOSURE.md` — раскрытие использования ИИ-инструментов (обязательно вести по правилам хакатона).

## Правила хакатона, влияющие на работу агента

1. Предметный код пишут сами студенты (п. 8.1 положения); каждый участник должен уметь объяснить код (п. 8.3). Не генерируйте крупные куски логики без запроса; объясняйте, что пишете.
2. Любое использование ИИ записывается в `DISCLOSURE.md` (какой инструмент, для какого модуля, кто проверил и принял результат).
3. Все тарифы — синтетические допущения модели, не выдавать за действующие тарифы RWB (п. 7.5).
4. Заглушки внешних систем (хаб, магистраль, оплата, приложение покупателя) — только под префиксом `/stub/*` и с плашкой «ИМИТАЦИЯ» в UI.

## Инварианты предметной логики

1. Деньги — в копейках, `int`/`bigint`, никакого `float`.
2. Все начисления — только через одну функцию проводки `post(...)`; сумма каждой проводки = 0 (двойная запись).
3. Одна единица товара — не больше одного активного резерва.
4. Статусы меняются только по разрешённым переходам конечного автомата, с проверкой версии записи.
5. Изменяющие запросы принимают ключ идемпотентности (заголовок `Idempotency-Key`).

Единицы измерения в логистике: деньги — копейки (int), время — минуты/часы, расстояния — км (float).

## Технологический стек

- **Backend:** Python 3.12, FastAPI ≥ 0.115, SQLAlchemy 2, Alembic, psycopg 3, Pydantic / pydantic-settings, networkx (поток минимальной стоимости в маршрутизации).
- **Frontend:** React 18, Vite 6, TypeScript ~5.6. Сборка: `tsc -b && vite build`.
- **БД:** PostgreSQL 16 (alpine).
- **Инфраструктура:** Docker Compose, GitHub Actions (`.github/workflows/ci.yml`).

## Структура кода

```
backend/
├── app/
│   ├── core/           конфиг (config.py), БД (db.py), логи (logging.py), роли (auth.py)
│   ├── api/            служебные эндпоинты: system.py (/health, /metrics, /me)
│   ├── modules/        предметные модули, по одному пакету на модуль
│   │   └── routing/    алгоритм логистики (реализован, см. ниже)
│   └── main.py         FastAPI-приложение, здесь подключаются роутеры модулей
├── migrations/         Alembic (env.py; версий пока нет — versions/ пустая)
└── tests/              pytest; test_system.py + tests/routing/

frontend/
└── src/                App.tsx (оболочка с переключателем ролей), api.ts, main.tsx, styles.css
```

Планируемые модули (пока реализован только `routing`): `network`, `inventory`, `orders`, `routing`, `ledger`, `ops`, `stubs` — ответственность каждого описана в `docs/03-architecture.md` и `backend/app/modules/README.md`.

### Соглашения для модуля в `backend/app/modules/<модуль>/`

- `models.py` — ORM-модели (наследуются от `app.core.db.Base`);
- `schemas.py` — Pydantic-схемы запросов и ответов;
- `service.py` — бизнес-логика без FastAPI;
- `router.py` — эндпоинты, подключаются в `app/main.py` (комментарий «Предметные роутеры подключаются здесь»);
- тесты — в `backend/tests/<модуль>/`.

Примечание: модуль `routing` отличается — он чисто алгоритмический (Pydantic-модели в `models.py`, без БД): `models.py` (входы/выходы, параметры модели v2), `network.py` (граф «дешёвых» рёбер, min-cost flow), `nightly.py` (ночной план), `daily.py` (дневной выбор варианта, закрытие ПВЗ), `compare.py` (сравнение трёх схем), `demo.py` (синтетический город), `router.py` (API `/routing/*`).

### API

- Служебное: `GET /health` (отвечает и без БД, статус `degraded`), `GET /metrics` (Prometheus), `GET /me`.
- Логистика: `POST /routing/plan`, `POST /routing/compare`, `GET/POST /routing/demo*` (демо-город живёт в памяти процесса; хранение в БД — задача модулей inventory/orders).
- Swagger: `http://localhost:8000/docs`.

## Аутентификация и роли

Настоящей авторизации нет — организаторы разрешают переключатель ролей. Роль передаётся заголовком `X-Role` (`pvz_operator`, `seller`, `logist`, `admin`). Проверка — зависимости `current_role` и `require_roles(...)` из `app/core/auth.py` (`Depends(require_roles(Role.ADMIN))`). JWT — в плане развития. Все запросы frontend идут через прокси Vite: `/api/*` → backend (см. `frontend/vite.config.ts`, `frontend/src/api.ts`).

## Команды (Makefile)

Все команды работы с кодом идут через контейнеры Docker Compose:

- `make up` — поднять всё (`docker compose up --build`); backend сам применяет миграции (`alembic upgrade head`) и стартует с `--reload`;
- `make test` — тесты backend в контейнере (`pytest -q`);
- `make lint` — линтер backend в контейнере (`ruff check .`);
- `make migration m="описание"` — новая миграция Alembic (autogenerate);
- `make migrate` — применить миграции;
- `make backup` / `make restore f=...` — дамп/восстановление БД (`pg_dump`);
- `make reset-db` — удалить данные БД (`down -v`);
- `make backend-dev` / `make frontend-dev` — локальный запуск без Docker (нужна БД: `docker compose up db`).

Перед первым запуском: `cp .env.example .env`. Порты на хосте настраиваются в `.env`: `DB_PORT` (5432), `API_PORT` (8000), `WEB_PORT` (5173). Настройки backend — `app/core/config.py` (pydantic-settings, читает `.env`); строка подключения `DATABASE_URL` по умолчанию `postgresql+psycopg://mesh:mesh@localhost:5432/mesh`, в Compose переопределяется на хост `db`.

Frontend локально: `cd frontend && npm install && npm run dev`; сборка — `npm run build`. Отдельного линтера/тестов у frontend нет; проверка — `tsc -b && vite build` в CI.

## CI (GitHub Actions)

`.github/workflows/ci.yml` на push в `main` и pull request:

- **backend** (ubuntu, Postgres 16 как сервис, Python 3.12): `pip install -e ".[dev]"` → `ruff check .` → `alembic upgrade head` → `pytest -q`. Значит, миграции должны применяться на пустую БД, а тесты не требуют живой БД (сейчас используют `fastapi.testclient.TestClient` без подключения).
- **frontend** (Node 20): `npm install` → `npm run build`.

## Стиль кода

- Python: ruff, line-length 100, target `py312`, правила `E, F, I, UP, B` (см. `backend/pyproject.toml`).
- Type hints в сигнатурах, современный синтаксис 3.12 (`X | None`, `StrEnum`).
- Комментарии и docstring — на русском, по делу (объясняют «почему», единицы измерения, ограничения).
- FastAPI-идиомы: `Annotated[..., Depends(...)]`, алиасы заголовков через `Annotated[str | None, Header(alias=...)]`.
- Pydantic-модели с `model_validator` для проверки ссылочной целостности входных данных.

## Тестирование

- pytest, конфиг в `backend/pyproject.toml` (`testpaths = ["tests"]`).
- Запуск: `make test` (в контейнере) или `cd backend && pytest -q` локально.
- Существующие тесты: `tests/test_system.py` (health, metrics, роли) и `tests/routing/test_routing.py` (алгоритм: попутные газели, вместимость, пересадки, крюки, целевой запас, закрытие ПВЗ, идемпотентность API, демо-город через `TestClient`).
- Стиль тестов: маленькие синтетические города, где ответ известен заранее; на каждый инвариант — отдельный тест; в тестах закреплены ранее исправленные ошибки (раздел «исправленные ошибки»).
- На каждый из четырёх инвариантов предметной логики (резервы, статусы, нулевая сумма проводок, идемпотентность) должен быть тест.

## Миграции и БД

- Alembic: `backend/alembic.ini`, `backend/migrations/env.py`. `target_metadata = app.core.db.Base.metadata`.
- Чтобы autogenerate увидел модели модуля, импортируйте их в `backend/migrations/env.py` (там есть закомментированный пример).
- Таблицы миграций пока нет — каталог `migrations/versions/` пуст; модель данных описана в `docs/03-architecture.md` (~19 таблиц).

## Безопасность и ограничения

- Не коммитьте `.env`; образец — `.env.example` (только синтетические креды `mesh`/`mesh`).
- Роль из заголовка — не авторизация: никаких секретов и реальных данных в демо.
- Демо-состояние `/routing/demo` хранится в памяти процесса — не полагайтесь на него как на хранилище.
- Заглушки внешних систем — только под `/stub/*`, в UI с плашкой «ИМИТАЦИЯ».
