## 1. Проект в пяти строках

**Mesh-доставка с хранением в ПВЗ** — хакатон RWB × ПГТУ, 25–26 ноября 2026, зачёт ПРО (Docker, Postgres, API, README обязательны).

Модель **v3**:
- товар, от которого покупатель отказался в ПВЗ, не едет обратно в хаб;
- сотрудник ПВЗ оценивает состояние товара; пригодный кладётся на mesh-полку этого ПВЗ;
- товар продаётся следующему покупателю в том же городе;
- между ПВЗ товар возят газели WB попутно, по своим обычным маршрутам;
- остановку в маршрут добавляем, только когда это дешевле хаба; иначе заказ идёт через хаб, и система объясняет почему.

**Если `docs/02`–`docs/04` расходятся с этим файлом, верен этот файл.** Документы ещё описывают модель v2 и обновляются задачей N10.

## 2. Решения команды (v3)

1. **Запас на mesh-полке — только отказы при получении.** Возврат после покупки всегда едет в хаб. Продавец сам в mesh ничего не сдаёт, квоты продавца нет.
2. **Сотрудник ПВЗ ставит оценку:**
   - `A` — не вскрыт → на полку;
   - `B` — вскрыт, упаковку восстановил → переупаковка → на полку;
   - `C` — восстановить нельзя или брак → в хаб.
3. **Полка работает как очередь:** под заказ берём самую старую единицу (FIFO по `shelved_at`).
4. **Доля склада ПВЗ под mesh — 10–50%, по умолчанию 25%; выбирает сам ПВЗ.** Место на полке: `занято_л + объём ≤ storage_total_l × mesh_share_pct / 100`. Не влезает → в хаб с причиной «полка заполнена».
5. **Хранение оплачивает маркетплейс по литрам:** ₽ за литр в сутки = место + труд сотрудника + прибыль владельца ПВЗ (три отдельных параметра).
6. **Выбор варианта заказа:** своя полка → соседний ПВЗ (с согласия покупателя) → попутная газель → хаб. Выгода ≤ 0 → хаб.
7. **Все тарифы — синтетические допущения**, не тарифы RWB (п. 7.5 положения). Числа берём только из `economics.params`, не придумываем.

**Решения кик-офа (N0, 26.11):**

| Вопрос | Решение |
| --- | --- |
| Возврат после покупки кладём на полку? | **Нет**: возврат после покупки всегда едет в хаб. На полку — только отказ при получении |
| Сколько отказ ждёт на полке до вывоза в хаб (D)? | **14 дней**, уведомление на **7-й**. На 14-й — перевезти туда, где спрос, или в хаб (что дешевле) |
| Кто платит переупаковку B? | **Маркетплейс** (как и хранение) |
| Что видит продавец в кабинете? | Деньги по каждому заказу — mesh против хаба; свои отказы на полках (где, сколько дней, оценка); сводка за период (сколько перепродано в городе и сколько сэкономлено) |

Новый неясный вопрос по бизнес-правилам — агент спрашивает человека и не додумывает.

## 5. Инварианты — нарушать нельзя

1. **Деньги — `int` в копейках** (`BigInteger` в БД). Никакого `float` в деньгах; округление — один раз, в конце.
2. **Все начисления — только через `ledger.post(...)`.** Сумма каждой проводки = 0, иначе `ValueError`. Записи не удаляются и не правятся: возврат — новая проводка с обратными знаками. У проводки есть `scheme`: `mesh` или `base` (как было бы через хаб) — по ним сравниваем схемы на одних заказах.
3. **Одна единица — не больше одного активного резерва** (частичный уникальный индекс `unit_id WHERE active`; конфликт → 409).
4. **Статусы меняются только по таблице разрешённых переходов**, с проверкой `version`: `UPDATE … WHERE version = :v`, иначе 409.
   - Заказ: `created → reserved → picked → in_transit → ready → issued`, плюс `cancelled`, `returned`, `rerouted`.
   - Единица: `on_shelf`, `reserved`, `in_transit`, `ready`, `issued`, `to_hub`, `at_hub`.
5. **Каждый изменяющий запрос принимает заголовок `Idempotency-Key`.** Хелпер в `app/core/idempotency.py` хранит ответ в `idempotency_keys`; повтор с тем же ключом возвращает тот же ответ и ничего не меняет.
6. **Заглушки внешних систем** (хаб, магистраль, оплата, приложение покупателя) — только под `/stub/*` и с плашкой «ИМИТАЦИЯ» в UI.

Счета проводок:
- участники: `seller:<id>`, `pvz:<id>`, `mp`;
- внешний мир: `ext:buyer`, `ext:labour`, `ext:van`, `ext:hub_ops`, `ext:trunk`, `ext:shrink`.

Тариф — перевод внутри цепочки (`mp → pvz:A`). Реальная затрата — уход наружу (`pvz:A → ext:labour`).

## 7. Что уже есть в коде

- **`backend/app/core/`** — конфиг (`config.py`, читает `.env`), БД (`db.py`, `Base`), JSON-логи, роли (`auth.py`: `require_roles(...)`).
- **`backend/app/api/system.py`** — `/health`, `/metrics` (Prometheus), `/me`.
- **`backend/app/modules/routing/`** — готовый алгоритм, 22 теста. Чистый Python без БД, вход — `City`:
  - `network.py` — граф попутных рёбер и поток минимальной стоимости;
  - `nightly.py` — ночной план: распределение, вставка остановок с лимитами ≤ 2 остановки и ≤ min(20 мин, 10% рейса);
  - `daily.py` — `choose()`: дневной выбор варианта с причинами; `close_pvz()`: перемаршрутизация при закрытии ПВЗ;
  - `compare.py` — три схемы на одних заказах;
  - `demo.py` — синтетический город: 11 ПВЗ, газели G1–G3;
  - `router.py` — эндпоинты `/routing/*`.
- **Как использовать routing из БД:** собрать `City` из таблиц и вызвать `nightly_plan` / `choose` / `close_pvz`. **Логику routing не переписывать** — расширять новыми файлами.
- **Модели БД (N1 готова):** 15 таблиц в `network`, `inventory`, `orders`, `ledger`, `ops` и миграция `init`. Ограничения держит сама база: CHECK на статусы, оценки, долю полки 10–50% и «возврат после покупки → только хаб»; частичный уникальный индекс «один активный резерв»; `version_id_col` у `Unit` и `Order` (устаревшая версия → `StaleDataError`, отдавать 409). Тесты — `backend/tests/test_db_schema.py`.
- **`app/modules/all_models.py`** импортирует модели всех модулей; его подключают `main.py`, `migrations/env.py` и тесты. Новый модуль с таблицами — одна строка туда.
- **Каркасы модулей** `stubs`, `analytics`, `scenarios`, `economics`: пустые `models.py` и `router.py` с префиксом из контракта, уже подключены. Роутеры остальных модулей тоже пустые. `app/seed.py` — заглушка до N2.
- **`frontend/`** — React 18 + Vite + TS, `recharts`, `openapi-typescript`. В `App.tsx` роли и их экраны уже подключены: `src/pages/{Pvz,PvzAnalytics,SellerAnalytics,Logist,Model,Scenarios}.tsx` — заглушки, их и наполняем.

## 8. Команды

- `cp .env.example .env` — один раз перед стартом.
- `make up` (`docker compose up --build`) — всё окружение. Backend **сам** выполняет `alembic upgrade head` при старте.
- `make test`, `make lint` — pytest и ruff в контейнере. Локально: `cd backend && pytest -q && ruff check .`.
- `make migration m="описание"` — миграция (autogenerate). Alembic видит модели через `app/modules/all_models.py`. Локально без Docker: `DATABASE_URL=postgresql+psycopg://mesh:mesh@localhost:<DB_PORT>/mesh`.
- `make reset-db` — удалить данные БД; `make fresh` — чистый стенд: удалить БД, поднять, засеять.
- `make check` — ruff, pytest и сборка фронта одной командой (локально); `make gen-api` — TS-типы из OpenAPI.
- Фронт: `cd frontend && npm install && npm run dev`; проверка — `npm run build`.
- Адреса: фронт — <http://localhost:5173>, API — <http://localhost:8000>, Swagger — <http://localhost:8000/docs>.

## 9. Проверка перед тем, как отдать задачу

- Backend: `pytest -q` и `ruff check .` зелёные; миграция применяется на пустую БД (это проверяет CI).
- Frontend: `npm run build` без ошибок.
- Перед слиянием в `main` и перед показом: `docker compose down -v && docker compose up --build`, затем `make seed` (цель появится в задаче N2).
- На каждый инвариант из раздела 5 — свой тест. Сценарные тесты проверяют числа, а не только «не упало».

## 10. Git

- Ветки: `u1/<задача>-<кратко>`, `u2/…`, `u3/…` — например, `u1/N4-refusals`.
- Сливаться в `main` каждые 45–60 минут и в вехи: Н+2:50, 10:30, 11:00, 13:40. Перед push — `git pull --rebase`.
- Коммиты маленькие, по смыслу, на русском: «Приём отказа: оценка A/B/C и лимит полки». Жюри смотрит историю.
- **Коммитит человек**, не агент, если человек прямо не попросил.
- Не коммитить `.env`, `node_modules`, `__pycache__`. Не делать `push --force` в `main`.

## 11. Чем агент заканчивает задачу

## 12. Стиль кода

- **Python 3.12:**
  - ruff: line-length 100, правила `E, F, I, UP, B`;
  - type hints, `X | None`, `StrEnum`;
  - FastAPI: `Annotated[..., Depends(...)]`;
  - модуль = `models.py` (ORM), `schemas.py` (Pydantic), `service.py` (логика без FastAPI), `router.py` (эндпоинты).
- **Комментарии и docstring — на русском:** объясняют «почему», единицы измерения и ограничения.
- **Тесты — на маленьких синтетических данных**, где ответ известен заранее.
- **Фронт:**
  - деньги приходят в копейках, показывать рубли с 2 знаками;
  - числа только из API, на фронте ничего не досчитывать;
  - новые тяжёлые зависимости — только после вопроса в чате; уже согласованы `recharts` и `openapi-typescript`.

## 13. Чего не делать

- Не менять файлы чужой роли и не переписывать `routing`.
- Не придумывать числа, тарифы и проценты: всё из `economics.params` или из вопроса человеку.
- Не отключать и не ослаблять тесты, чтобы они прошли.
- Не хранить состояние в памяти процесса для новых модулей: всё в Postgres. Исключение — готовое демо `/routing/demo`.
- Не выдавать тарифы за реальные тарифы RWB; не использовать реальные персональные данные.
