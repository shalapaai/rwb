# 03 · Архитектура MVP

Три контейнера (PostgreSQL, backend, frontend), монолит с модулями. Экраны аналитики, отчёт по сценариям и таблицы для презентации читают одни и те же проводки, поэтому числа в демо и на слайдах не расходятся.

## Модули backend

| Модуль | Отвечает за |
| --- | --- |
| `network` | Узлы (ПВЗ, хаб/СЦ, продавец), граф дорог, статусы и ёмкость ПВЗ |
| `inventory` | SKU, партии, единицы, ячейки, резервы |
| `orders` | Заказы, строки, статусная машина |
| `routing` | Ночной план газелей и выбор варианта исполнения заказа днём; кандидаты с причинами; перемаршрутизация при сбое |
| `ledger` | Тарифы, двойная запись, отчёты по сторонам |
| `ops` | Задания ПВЗ, инциденты, возвраты, неликвид, `sim_clock` |
| `stubs` | Хаб, магистраль, платёжный шлюз, приложение покупателя — `/stub/*`, плашка «ИМИТАЦИЯ» в UI |

Одно приложение с переключателем ролей: оператор ПВЗ, продавец, логист, администратор сценариев. Организаторы прямо разрешают переключатель вместо авторизации.

## Четыре инварианта (на каждый — тест)

1. **Одна единица — не больше одного активного резерва** (частичный уникальный индекс). Нет повторного списания одного и того же товара.
2. **Статусы меняются только по разрешённым переходам** конечного автомата, с проверкой версии записи.
3. **Каждое движение денег — проводка с нулевой суммой.** Это программная проверка «переводы не создают прибыль цепочки».
4. **Каждый изменяющий запрос принимает ключ идемпотентности:** повторный скан не создаёт вторую операцию.

Статусы заказа: `created → reserved → picked → in_transit → ready → issued` (плюс `returned`, `rerouted`, `cancelled`).

## Деньги: двойная запись

Две разные проверки:

1. Деньги не появляются из ниоткуда: сумма каждой проводки равна нулю.
2. Выгода цепочки — реальная экономия: в те же проводки пишутся реальные внешние затраты.

**Счета**

| Тип | Примеры | В цепочке? |
| --- | --- | --- |
| Участники | `seller:S-01`, `pvz:A`, `pvz:B`, `mp` | да |
| Внешний мир — деньги | `ext:buyer` | нет |
| Внешний мир — затраты | `ext:labour`, `ext:van`, `ext:hub_ops`, `ext:trunk`, `ext:shrink` | нет |

Тариф — перевод внутри цепочки (`mp → pvz:A`). Затрата — уход наружу (`pvz:A → ext:labour`, `mp → ext:van`).

**Правила**

- Деньги — в копейках целыми числами (`bigint`), никакого `float`.
- Все начисления — только через одну функцию `post(scheme, kind, order_id, legs, key)`, которая проверяет `sum(legs) == 0`.
- Деление с остатком: стоимость крюка 130 ₽ на 7 единиц — первым по 18,57 ₽, последней остаток, чтобы сумма была ровно 130,00 ₽.
- Возврат — новая проводка с обратными знаками, записи не удаляются.
- Каждая проводка помечена схемой `mesh` или `base`, чтобы сравнивать схемы на одних заказах.

**Тесты**

- Нет ни одной проводки с ненулевой суммой.
- Сумма изменений сторон = эффект цепочки.
- Эффект цепочки = разница внешних затрат базы и mesh. Если прибыль «нарисована» тарифом, этот тест упадёт.

На экране аналитики: «Проверка: сумма выгод сторон = экономия цепочки ✓».

## Маршрутизация: ночной план газелей

Газели от хаба каждый день проезжают 5–15 ПВЗ по маршруту, который строится заново под расстояния и сезон. Mesh-перемещение для них — ещё одна пара остановок «забрать в А → отдать в Б» в том же плане. В исследовании операций это задача маршрутизации с забором и доставкой (pickup and delivery VRP).

**Входы:** граф дорог (× сезонный коэффициент), базовые маршруты газелей на завтра и их загрузка по отрезкам, остатки на полках, заказы со сроками, прогноз спроса по районам, ограничения ПВЗ, цены.

**Шаги**

1. **Граф «дешёвых» рёбер.** Попутное ребро: газель заезжает в А раньше Б и на отрезке есть место. Ребро пересадки: две газели бывают в одном ПВЗ. Ребро крюка — кандидат на вставку ПВЗ в маршрут. Ребро хаба — запасное.
2. **Целевой запас по районам.** Прогноз на 2–3 дня с запасом по формуле «газетчика», полка ≤ 25%. Дефицит — спрос на переброску, излишек — источник.
3. **Распределение товара сразу для всех.** Поток минимальной стоимости по каждому артикулу (`networkx.min_cost_flow`). Встречные перевозки исчезают. Приоритет: заказы → возвраты и залежалое → переброска под прогноз.
4. **Правка маршрутов, только если окупается.** Смена порядка, вставка ПВЗ, пересадка. Лимиты: +10% или ~20 мин к маршруту, ≤ 2 новых остановки, окна ПВЗ и сроки хаба соблюдены, 10% места в запасе. Крюк делаем, только если выгода всех единиц на остановке больше его цены (~130 ₽ → от ~5 единиц).
5. **Повтор 2–3 раза.** Вставленный заезд становится бесплатным для остальных товаров. Затем локальный поиск (упрощённый ALNS).
6. **Выход:** новые маршруты, задания ПВЗ на отбор и приём, таблица цены обслуживания «откуда → куда → ₽, часы» для дневных ответов.

**Целевая функция:** максимум Σ экономии заказов + Σ ожидаемой экономии переброски − Σ цены правок − хранение − λ × число правок.

```python
def nightly_plan(roads, base_routes, stock, orders, forecast, params):
    routes = base_routes
    for _ in range(3):                                    # шаг 5: повторы
        G = build_cheap_graph(routes, roads, params)      # шаг 1
        targets = target_stock(forecast, stock, params)   # шаг 2
        flows = min_cost_flow(G, stock, orders, targets)  # шаг 3
        edits = [e for e in candidate_edits(flows.unserved, routes, roads) if gain(e) > 0]
        new_routes = apply_best(routes, sorted(edits, key=gain, reverse=True),
                                limits=params.limits)     # шаг 4
        if total_profit(new_routes, flows) <= total_profit(routes, flows):
            break
        routes = new_routes
    routes, flows = local_search(routes, flows, time_limit=60)
    return routes, flows, cost_to_serve_table(routes, flows)  # шаг 6
```

**Днём при заказе** — быстрый ответ по таблице цены обслуживания:

1. Найти единицы SKU со свободным остатком.
2. Для каждого варианта (свой ПВЗ → соседний ПВЗ → газель → хаб) посчитать `цена + λ·часы`, λ = 0,5 ₽/ч на единицу.
3. Отбросить нарушающие ограничения: узел закрыт, нет места в ячейках, газель уже прошла А, срок хуже обещанного.
4. Выбрать минимум и сохранить всех кандидатов с причинами («ПВЗ-7 закрыт», «газель уже прошла ПВЗ-A», «дороже хаба на 12 ₽»). Их видит оператор и логист.
5. Если выгода против хаба ≤ 0 — заказ идёт через хаб. Это и есть граница на числах.

**Перемаршрутизация при сбое.** Инцидент помечает узел или остановку недоступной. Система находит заказы с незавершёнными плечами через неё, пересчитывает только пострадавшие потоки от текущего места единицы, создаёт новую версию плана и записывает доп. затраты, сдвиг срока, виновника и уведомления.

**Что реализовано** (`backend/app/modules/routing`)

| Шаг | Как сделано |
| --- | --- |
| 1. Граф | Узел на каждую остановку газели; рёбра: посадка, проезд (ёмкость = свободные места на отрезке, газель освобождается по ходу), пересадка (вторая газель позже минимум на 15 мин), высадка; закрытый ПВЗ газель проезжает, но не обслуживает. Лимит mesh-операций ПВЗ (60/день) — на посадку и высадку |
| 2. Целевой запас | `S = d·T + z·σ·√T`, T = 2 дня, z = 1,28, не больше свободной полки; привезти под прогноз можно не больше, чем осталось места на полке — общий лимит в литрах для всех артикулов |
| 3. Поток | `networkx.min_cost_flow` по каждому артикулу; цена ребра = деньги + λ·часы; награда за каждую единицу, лежащую к вечеру в ПВЗ в пределах цели (своя или привезённая — один общий узел цели), = 0,6 × (хаб − свой ПВЗ). Артикулы — по убыванию спроса, каждый забирает свою часть мест |
| 4. Правка маршрутов | Для каждой газели и каждого ПВЗ вне её маршрута — самое дешёвое место вставки (с учётом стоянки на предыдущей остановке); крюк принимается, если план дешевеет больше цены крюка; лимиты: min(20 мин, 10% рейса), ≤ 2 новых остановки |
| 5. Повторы | До 5 итераций, пока есть выгодная вставка |
| 6. Днём | Кандидаты «свой → соседний (с согласием) → газель (Дейкстра по остаточным местам) → хаб» с причинами отказа; проверка обещанного срока; закрытие ПВЗ: товар едет в закрытый ПВЗ — выгрузка в ближайший ПВЗ той же газели, который она ещё не проехала (с согласием, если есть места), иначе завтрашний рейс; товар забирают из закрытого ПВЗ или пересаживают в нём — вариант выбирается заново; штраф 20 ₽/ед. |

API: `POST /routing/plan`, `POST /routing/compare`, `/routing/demo` (`reset`, `compare`, `orders`, `incidents/{pvz}`); изменяющие демо-запросы принимают заголовок `Idempotency-Key`. Ограничения: дедлайн заказа проверяется днём, в ночном плане — нет; пересадка не расходует лимит операций ПВЗ; переброски под прогноз в закрывшийся ПВЗ днём не перенаправляются.

**В плане развития:** совместная оптимизация хаб-доставки и mesh (OR-Tools, ALNS — Ropke & Pisinger, 2006), точный многопродуктовый поток, отдельный челнок для плотных пар (от ~100 ед.), окна ПВЗ по времени, управление спросом («заберите сегодня в соседнем ПВЗ», «+1 день со скидкой»).

**Результат на демо-городе** (11 ПВЗ, 3 газели, 19 единиц в заказах; `GET /routing/demo/compare`):

| Схема | ₽ на единицу | Средний срок | Без хаба | Доп. км |
| --- | --- | --- | --- | --- |
| Всё через хаб | 60,40 | 36,0 ч | 0% | 0 |
| По одному заказу (жадно) | 44,33 | 21,2 ч | 53% | 0 |
| Ночной план | 42,78 | 12,3 ч | 90% | 4,0 |

**Как доказать выгоду:** прогнать один синтетический город через три схемы — «всё через хаб», «жадная вставка», «полный цикл» — и сравнить стоимость, срок, км и загрузку ПВЗ.

## Эксплуатация

| Область | В MVP | План развития |
| --- | --- | --- |
| Доступ | Переключатель ролей, проверка роли на эндпоинте | JWT, единый вход RWB, mTLS, аудит |

| Рост | Монолит с модулями | Шардирование по городам, реплика аналитики, партиции проводок; ночной план — отдельный воркер на город |
