# 03 · Архитектура MVP

Три контейнера (PostgreSQL, backend, frontend), монолит с модулями. Экраны аналитики, отчёт по сценариям и таблицы для презентации читают одни и те же проводки, поэтому числа в демо и на слайдах не расходятся.

## Модули backend

| Модуль | Отвечает за |
| --- | --- |
| `network` | Узлы (ПВЗ, СЦ, хаб, продавец), рёбра с расписанием, статусы и ёмкость |
| `inventory` | SKU, партии, единицы, ячейки, резервы |
| `orders` | Заказы, строки, статусная машина |
| `routing` | Выбор маршрута, кандидаты с причинами, перемаршрутизация при инциденте |
| `ledger` | Тарифы, двойная запись, отчёты по сторонам |
| `ops` | Задания ПВЗ, инциденты, возвраты, длительное хранение, `sim_clock` |
| `stubs` | Хаб, магистраль, платёжный шлюз, приложение покупателя — `/stub/*`, плашка «ИМИТАЦИЯ» в UI |

Одно приложение с ролями: оператор ПВЗ, продавец, логист, администратор сценариев.

## Модель данных (~18 таблиц)

| Группа | Таблицы | Ключевые поля |
| --- | --- | --- |
| Сеть | `nodes`, `links` | тип, город, статус, ёмкость и лимит mesh-полки; у рёбер — вид транспорта, стоимость, длительность, расписание, флаг «заглушка» |
| Товар | `sellers`, `products`, `lots`, `units`, `storage_cells` | SKU (цена, объём, допуск в mesh); партия (продавец, дата приёмки, тариф); единица со штрихкодом, узлом, ячейкой, статусом и версией |
| Заказ | `orders`, `order_lines`, `reservations` | ПВЗ выдачи, статус, обещанный срок; резерв единицы со сроком истечения |
| Маршрут | `route_plans`, `route_segments` | версия плана, схема, стоимость, ETA, основания выбора (JSON с кандидатами); сегменты со статусом |
| Операции | `tasks`, `incidents`, `returns` | задания ПВЗ; инциденты с виновником и штрафом; возвраты с решением |
| Деньги | `tariffs`, `ledger_txn`, `ledger_entry` | версионные тарифы; проводки по двойной записи |
| Служебное | `notifications`, `events`, `sim_clock`, `idempotency_keys` | уведомления; журнал событий; сдвиг тестового времени; ключи повторных запросов |

## Четыре инварианта (на каждый — тест)

1. **Одна единица — не больше одного активного резерва** (частичный уникальный индекс). Нет повторного списания одного и того же товара.
2. **Статусы меняются только по разрешённым переходам** конечного автомата, с проверкой версии записи.
3. **Каждое движение денег — проводка с нулевой суммой.** Программная проверка «переводы не создают прибыль цепочки».
4. **Каждый изменяющий запрос принимает ключ идемпотентности:** повторный скан не создаёт вторую операцию.

Статусы заказа: `created → reserved → picked → in_transit → ready → issued` (плюс `returned`, `rerouted`, `cancelled`).

## Деньги: двойная запись

Две разные проверки:

1. Деньги не появляются из ниоткуда — сумма каждой проводки равна нулю.
2. Выгода цепочки — реальная экономия: в те же проводки пишутся реальные внешние затраты.

**Счета**

| Тип | Примеры | В цепочке? |
| --- | --- | --- |
| Участники | `seller:S-01`, `pvz:A`, `pvz:B`, `mp` | да |
| Внешний мир — деньги | `ext:buyer` | нет |
| Внешний мир — затраты | `ext:labour`, `ext:carrier`, `ext:hub_ops`, `ext:trunk`, `ext:shrink` | нет |

Тариф — перевод внутри цепочки (`mp → pvz:A`). Затрата — уход наружу (`pvz:A → ext:labour`).

**Правила**

- Деньги — в копейках целыми числами (`bigint`), никакого `float`.
- Все начисления — только через одну функцию `post(scheme, kind, order_id, legs, key)`, которая проверяет `sum(legs) == 0`.
- Деление с остатком: 2 400 ₽ на 180 единиц — первым по 13,33 ₽, последней остаток, чтобы сумма была ровно 2 400,00 ₽.
- Возврат — новая проводка с обратными знаками, записи не удаляются.
- Каждая проводка помечена схемой `mesh` или `base`, чтобы сравнивать схемы на одних данных.

**Тесты**

- Нет ни одной проводки с ненулевой суммой.
- Сумма изменений сторон = эффект цепочки.
- Эффект цепочки = разница внешних затрат базы и mesh. Если прибыль «нарисована» тарифом, этот тест упадёт.

На экране аналитики: «Проверка: сумма выгод сторон = экономия цепочки = 28,30 ₽ ✓».

## Маршрутизация

Для MVP это кратчайший путь (Дейкстра) по небольшому графу с расписанием, а не VRP. Кольцевой маршрут курьера фиксирован заранее.

**Граф.** Узлы: ПВЗ, СЦ, хабы (заглушка), точки продавцов — со статусом и свободной ёмкостью. Рёбра: mesh-рейс (отправления 11:00 и 17:00), штатные рейсы СЦ ↔ ПВЗ, магистраль (заглушка). У каждого ребра — стоимость, длительность и время отсечки.

**Алгоритм выбора**

1. Найти все узлы со свободным остатком SKU.
2. Для каждого источника найти самое раннее прибытие в ПВЗ покупателя и посчитать обобщённую стоимость: рубли + λ × часы, λ = 0,5 ₽/ч на единицу.
3. Отбросить кандидатов, нарушающих ограничения: узел недоступен, нет свободных ячеек, рейс ушёл, срок хуже обещанного, превышен лимит полки.
4. Выбрать минимум и сохранить всех кандидатов с причинами («ПВЗ-7 закрыт», «рейс 11:00 ушёл», «дороже на 12 ₽»). Их видит оператор.
5. **Правило рейса:** если прогноз трансферов на рейс меньше порога (~104 ед.), рейс не запускается, трансферы идут через СЦ.

**Кольцо курьера.** Один фургон за 2–3 ч объезжает 15–25 ПВЗ. Город делится на кластеры (k-means по координатам), у каждого своё кольцо. Порядок объезда — ближайший сосед + 2-opt, считается один раз. Направление кольца важно: товар A → C доедет в этом рейсе, C → A — только на следующем проходе. В MVP так и считаем срок честно; два круга или pickup-and-delivery VRP (OR-Tools) — в план развития.

**Межкластерные заказы**

1. Не создавать межкластерный спрос: держать запас ходового товара в каждом кластере.
2. Плановое ночное выравнивание запасов между кластерами через СЦ партиями.
3. Срочный заказ: соседний кластер — через общую пересадочную точку колец в тот же день; дальний — через СЦ на следующий день.

Нагрузка на СЦ падает: внутрикластерные заказы туда не попадают вообще.

**Перемаршрутизация при сбое.** Инцидент помечает узел или ребро недоступным. Система находит заказы с незавершёнными сегментами через него, пересчитывает путь от текущего места единицы, создаёт новую версию плана и записывает доп. затраты, сдвиг срока, виновника и уведомления.

Граф города — до нескольких сотен узлов, расчёт на заказ — миллисекунды (`networkx` или свой Дейкстра).

## Эксплуатация

| Область | В MVP | План развития |
| --- | --- | --- |
| Доступ | Роли, JWT, проверка прав на эндпоинте | Единый вход RWB, mTLS, аудит |
| Повторные запросы | Ключ идемпотентности, уникальные индексы, версии записей | Outbox + брокер событий |
| Сбои | Инцидент → пересчёт маршрута → уведомление | Офлайн-режим приложения ПВЗ, размыкатели |
| Логи и метрики | JSON-логи, журнал событий, `/metrics` | Prometheus, Grafana, OpenTelemetry |
| Бэкапы | `pg_dump` по расписанию, скрипт восстановления | WAL-архив, RPO ≤ 5 мин, RTO ≤ 30 мин |
| Доступность | Один экземпляр | 99,9% для API ПВЗ, 99,5% для аналитики |
| Рост | Монолит с модулями | Шардирование по городским кластерам, реплика аналитики, партиции проводок |
