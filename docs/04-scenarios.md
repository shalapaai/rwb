# 04 · Пять сценариев v3

Сценарии задают условия приёмки для одного демо-города. Приём отказа и полку уже можно проверить через API ПВЗ, выбор пути — в демо маршрутизации, экономику — через `/model/*`. Сквозные действия с заказом, возвратом, инцидентом и часами описаны как ожидаемое поведение для задач M1, F1 и F2. Для сравнения фиксируем артикул, ID единицы и заказа, статус, доступный остаток, причину выбора и связанные проводки. Роль передаётся в `X-Role`. Все тарифы — синтетические допущения по п. 7.5 положения. [Контракт API и решения кик-офа](../AGENTS.md)

## 1. Отказ в ПВЗ-A → заказ в ПВЗ-B → выдача

1. Покупатель отказывается от SKU-001 при получении в ПВЗ-A. Упаковка цела, оператор ставит A. На полке есть место. Для сквозной проверки этой конкретной единицы берём полку без более старых единиц того же SKU.
2. Оператор регистрирует отказ через `POST /pvz/ПВЗ-A/refusals` с телом `{"sku_id":"SKU-001","grade":"A"}` и заголовком `Idempotency-Key`. В ответе ожидаем `placement=shelf` и `unit_id`. Единица получает статус `on_shelf`. Повтор запроса с тем же ключом возвращает тот же результат.
3. Следующий покупатель заказывает SKU-001 в ПВЗ-B. В B товара нет, на соседний пункт покупатель не согласился. Газель G1 проезжает A раньше B, в кузове есть место, попутное исполнение выгодно. Система резервирует самую старую подходящую единицу в A.
4. Оператор A отбирает товар к рейсу. G1 забирает его в A и доставляет в B. Оператор B принимает и выдаёт товар. Заказ проходит `created → reserved → picked → in_transit → ready → issued`.

**Что проверить.** В A появился один пригодный отказ. После резерва он недоступен для другого заказа, а после отправки освобождает место. В B приёмка переводит товар в `ready`, выдача — в `issued`. За проверку маркетплейс начисляет ПВЗ 15,00 ₽. Эту выплату видно отдельно от расхода на труд. Для каждой проводки сумма по счетам равна нулю. [Тесты приёма отказов](../backend/tests/inventory/test_refusals.py)

## 2. Заказ без городского остатка

Покупатель заказывает SKU-002 в ПВЗ-B. Подходящих единиц на mesh-полках города нет. Путь идёт через хаб и магистраль. Хаб и внешняя доставка в интерфейсе помечены «ИМИТАЦИЯ».

**Что проверить.** В выборе маршрута указана причина «нет городского запаса». На полках нет нового резерва. Ориентир для следующего городского заказа из хаба — **60,40 ₽** (`hub_order_kop`). В расчёте на уже случившийся отказ база составляет **97,40 ₽** и включает также обратный путь отказа в хаб. [Расчёт на отказ и следующий заказ](02-business-model.md)

## 3. Возврат после выдачи → оценка → хаб

Покупатель возвращает в ПВЗ-B товар, выданный в сценарии 1. Оператор находит выданную единицу по заказу, фиксирует оценку состояния и оформляет возврат после покупки. По решению кик-офа даже при оценке A возврат едет в хаб.

**Что проверить.** Заказ получает статус `returned`, единица — `to_hub`. Доступный остаток B не увеличивается. Сторнирование оформляется новыми обратными проводками со ссылкой на заказ. Исходные проводки выдачи сохраняются, сумма записей каждой обратной проводки равна нулю.

## 4. ПВЗ-B закрылся, пока товар в G1

Этот случай начинается с копии состояния сценария 1 после погрузки в A, до выдачи. ПВЗ-B закрывается, пока газель в пути. Если ПВЗ-C ещё впереди по маршруту и покупатель согласен, заказ можно перенаправить в C. Если C уже проехали или покупатель отказался от смены пункта, система пересчитывает доступные варианты и сообщает новый путь и срок.

**Что проверить.** Для согласившегося покупателя в демо выбирается C, пока остановка достижима. После проезда C этот вариант исключается. Единица сохраняет связь с заказом, повторной выдачи и второго активного резерва нет. [Автотест закрытия пункта на маршруте G1](../backend/tests/routing/test_routing.py)

## 5. Отказ остаётся без спроса

На полке в ПВЗ-A лежит пригодный отказ A объёмом 2 л. Заказов на этот товар нет. В действующем сценарии на 7-е сутки отправляется уведомление, на 14-е сравниваются перемещение туда, где есть спрос, и вывоз в хаб. При отсутствии спроса во всём городе выбирается хаб. После вывоза место освобождается, начисление за хранение в A прекращается.

**Сравнение со сценарием на 30 суток из роадмапа.** Для расчётного эксперимента оставляем тот же отказ на исходной полке 30 суток. В обоих вариантах спрос нулевой, поэтому калькулятор учитывает хранение за весь срок и затем путь через хаб. Запрос — `GET /model/unit-economics?grade=A&volume_l=2&demand_per_day=0&shelf_days=30`. Для действующего срока замените `shelf_days` на `14`.

| Срок | Выплата ПВЗ за хранение, ₽ | База, ₽ | Mesh, ₽ | Эффект цепочки, ₽ |
| --- | ---: | ---: | ---: | ---: |
| 14 суток · правило v3 | 4,20 | 97,40 | 116,70 | −19,30 |
| 30 суток · стресс-сценарий | 9,00 | 97,40 | 119,90 | −22,50 |

**Что проверить.** Уведомление само по себе не меняет остаток. Вывоз снимает единицу с полки один раз. При нулевом спросе эффект в обеих строках отрицательный. Для сопоставления с обычным спросом `GET /model/boundary` показывает, при какой интенсивности местных заказов эффект становится положительным.
